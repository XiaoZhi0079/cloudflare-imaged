# 近似 16:9 轮播图片资格设计

## 背景

当前轮播资格要求图片为精确 `16:9`，并且不低于 `1920×1080`。这会拒绝 `1672×941` 等因导出取整或轻微裁边而接近 `16:9` 的优质图片，也会在只放宽比例后继续被旧的最低分辨率门槛拒绝。

本次调整同时放宽比例和最低尺寸。Hero 舞台仍保持精确 `16:9`，图片继续使用 `object-fit: contain` 完整展示，不裁切、不拉伸，也不生成派生图。

## 目标

- 实际尺寸为 `1672×941` 的图片可以加入轮播。
- 接受与 `16:9` 的相对偏差不超过 `0.5%` 的横向图片。
- 最低尺寸调整为 `1600×900`，继续排除 `1280×720` 等较低分辨率素材。
- 服务端写入校验、管理端候选筛选、分辨率档位、提示文案和文档使用同一套共享规则。
- 保持现有 API 字段和内部档位键兼容，不需要 D1 migration。

## 资格规则

### 尺寸有效性

`width` 和 `height` 必须都是大于零的安全整数。缺失、非整数、非有限值或超出 JavaScript 安全整数范围时，图片状态为“尺寸未知”，不能作为新的轮播图片。

### 比例容差

目标比例为 `16:9`，允许目标相对误差 `±0.5%`，闭区间约为：

```text
1.7688888889 <= width / height <= 1.7866666667
```

实现使用 `BigInt` 交叉乘法，不使用浮点除法：

```text
abs(9 * width - 16 * height) * 1000 <= 16 * height * 5
```

边界值包含在合格范围内。`1672×941` 的比例约为 `1.776833`，相对偏差约为 `0.0531%`，因此通过比例判断。

### 最低分辨率

图片必须同时满足：

```text
width >= 1600
height >= 900
```

最终资格为“尺寸有效、比例在容差内、宽高均达到最低值”三个条件的交集。`1600×900` 和 `1672×941` 合格，`1280×720` 因分辨率不足而不合格。比例超出容差时优先显示“比例不符”；比例合格但尺寸过小时显示“分辨率不足”。

## 共享分类结果

`classifyFeaturedImage()` 继续作为唯一资格来源，并返回：

- 保留 `isExactSixteenNine`，只表示是否数学上精确为 `16:9`，避免改变现有字段含义。
- 新增 `isApproximatelySixteenNine`，表示是否落入 `±0.5%` 容差；轮播资格改用此字段。
- `meetsMinimum` 改为检查 `1600×900`。
- `eligible` 等于 `isApproximatelySixteenNine && meetsMinimum`。
- `reason` 和 `statusLabel` 沿用“尺寸未知”“比例不符”“分辨率不足”“轮播可用”。

这样 `1672×941` 会同时得到 `isExactSixteenNine: false`、`isApproximatelySixteenNine: true` 和 `eligible: true`，既保留准确语义，也让旧消费者继续读取已有字段。

## 分辨率档位

合格图片继续按宽高双阈值分类：

| 内部键 | 条件 | 管理端名称 |
| --- | --- | --- |
| `4k` | `width >= 3840 && height >= 2160` | `4K` |
| `2k` | 未达到 4K，且 `width >= 2560 && height >= 1440` | `2K` |
| `1k` | 其余合格图片 | `HD+ / 900p+` |

保留内部键 `1k`，避免改变现有筛选状态和 API 数据形状；只把不再准确的可见名称“1K / 1080p”改为“HD+ / 900p+”。档位边界仍要求宽和高同时达到门槛，避免把短边不足的图片标成对应标准分辨率。

## 数据流与界面行为

图片上传时已从解码结果获得宽高并写入 D1，本次不重新读取原图，也不增加数据库字段或迁移。

管理图片列表继续只负责搜索与标签匹配。轮播选择器读取管理 API 返回的 `featuredEligibility`：

1. 只为 `eligible === true` 且具有有效档位的图片创建候选项。
2. “全部可用、4K、2K、HD+ / 900p+”只在内存中切换，不重新查询 D1。
3. 候选项继续显示实际宽高和档位。
4. 已在轮播中但不符合当前规则的 legacy 项仍按现有逻辑保留，只有管理员明确移除才删除。

服务端保存站点配置时重新调用共享规则，拒绝任何不合格的新选择。错误文案改为“图片必须接近 16:9（误差不超过 0.5%）且至少 1600×900”，防止前端显示可选而服务端仍按旧规则拒绝。

## Hero 展示

Hero 容器继续保持响应式精确 `16:9`，图片继续 `contain` 居中完整展示。近似比例图片可能产生极细的上下或左右留边，这是完整展示且不变形的预期结果。本次不改变 Hero 高度、轮播交互或文本布局。

## 错误处理与兼容性

- 尺寸未知或非法：不可新选，返回“尺寸未知”。
- 比例超出 `±0.5%`：不可新选，返回“比例不符”。
- 比例合格但低于 `1600×900`：不可新选，返回“分辨率不足”。
- 原有精确 `16:9` 且至少 `1920×1080` 的图片仍全部合格，不产生收紧回归。
- 本次只放宽资格，因此不会让当前合格轮播项变为不合格。
- 不修改持久化结构，不运行 D1 migration。

## 测试与验收

先补失败测试，再修改实现。测试至少覆盖：

- `1672×941` 合格，且精确比例字段为 `false`、近似比例字段为 `true`。
- `1600×900` 最低边界合格，`1280×720` 因分辨率不足而拒绝。
- `1920×1080`、`2560×1440`、`3840×2160` 和更高精确比例素材保持原档位。
- 比例容差的上下边界包含，边界外的最邻近可构造尺寸拒绝。
- 明显错误比例、未知尺寸、负数、小数和超出安全整数范围拒绝。
- Repository 和站点 API 原子拒绝不合格 ID，并使用新规则文案。
- 轮播选择器只包含合格候选，档位标签和计数使用新名称，跨档选择保持。
- 全量自动化测试通过，静态检查不再出现面向当前功能的“精确 16:9 且至少 1920×1080”文案。

验收只使用合成的宽高元数据和非图片 DOM/HTTP 检查。不得下载、打开、截图、解码或分析图库中的任何图片。
